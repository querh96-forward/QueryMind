# QueryMind 语义检索优化与复测报告

本文记录语义检索方案、Docker验证结果与SQL端到端复测。默认应用地址：[打开 QueryMind](http://127.0.0.1:6006)。

检索评测时间（UTC）：2026-09-19T07:46:46.587529+00:00。SQL 复测时间（UTC）：2026-09-19T07:47:19.262404+00:00。

## 实现内容

- 独立配置Embedding服务的密钥、地址、模型、维度与超时；本次评测使用 `text-embedding-v4`、1024维。
- 文档入库和问题检索均调用真实向量接口；48条知识已完成向量化。原哈希向量仅保留为显式基线或离线测试模式，接口失败不会静默降级。
- 修复原关键词召回将相似度为零的文档送入 RRF 融合的问题。相似度为零时没有词面证据，不应凭文档ID顺序产生排名票数。
- 索引按提供方、模型、维度、端点摘要和知识库内容版本隔离；事务内完成索引构建，保留旧索引，重复启动复用已建版本。Redis 同时隔离索引版本与检索策略。
- 增加真实 Embedding Token 统计：索引构建与单次查询分别记录，缓存命中用量为零。
- `.env` 与 `.env.example` 已对齐为24项配置，聊天使用 `LLM_*`，向量使用 `EMBEDDING_*`。旧聊天变量别名兼容。示例文件没有密钥，本地 `.env` 权限为600，并被 Git 与 Docker 构建排除。

## 检索效果

Recall@5 表示目标知识是否出现在返回的前5条中。它不是最终回答正确率。

| 题集 | 原哈希向量＋原融合 | 语义向量＋修正融合 |
|---|---:|---:|
| 原有题，12题 | 11/12（91.67%） | 12/12（100.00%） |
| 同义改写诊断题，20题 | 3/20（15.00%） | 20/20（100.00%） |
| 本轮新增保留题，16题 | 3/16（18.75%） | 15/16（93.75%） |
| 合计，48题 | 17/48（35.42%） | 47/48（97.92%） |

总 Recall@5 从35.42%到97.92%，提高62.50个百分点。MRR@5 从0.2969到0.7285；MRR 越高说明目标平均越靠前。

原有12题和新增20道改写题构成诊断集。首轮只换向量模型时，语义向量单独检索命中31/32，而原融合只命中20/32，因此进一步定位到零相似度候选补位的问题。首轮完整结果保留在 [Embedding 替换实验](../evals/reports/semantic-retrieval-embedding-only.json)。随后固定新增16题进行本轮保留验证，题目与标签没有根据最终结果调整。知识库、RRF等权权重、常数60和候选上限保持一致。

| 对照方案（48题） | Recall@5 | MRR@5 |
|---|---:|---:|
| 哈希256 + 原融合 | 35.42% | 0.2969 |
| 哈希256 + 修正融合 | 45.83% | 0.3347 |
| 语义1024 + 原融合 | 56.25% | 0.3885 |
| 语义1024 + 修正融合（当前默认） | 97.92% | 0.7285 |
| 哈希256，仅向量 | 43.75% | 0.3052 |
| 语义1024，仅向量 | 97.92% | 0.9444 |

纯语义向量的首位命中率为91.67%、MRR@5为0.9444，高于当前混合方案；混合方案并非所有指标都最优。当前按 top-5 提供知识上下文；不同方案在个别题上互有得失。后续若调整融合权重或加入重排，需要使用新的验证集。

唯一混合检索未命中的保留题为 `heldout_04`：“订单还没寄出的情况下，是否应该纳入从下单到出库所需天数的平均值？”目标是 `metric_shipping`，当前前5条偏向订单结构和汇总知识。该失败已保留，未修改标签掩盖问题。

每个问题只有一个人工标注目标；样本规模仅48题，其中32题参与过诊断。以上不能视为通用线上检索准确率。

## SQL 端到端复测

聊天模型 `qwen3.8-max`，真实API，沿用原24题、参考SQL与严格评分规则。题目的SQL保留组已在上一阶段运行过，本轮属于回归验证，不宣称全新未见测试。

| 指标 | 本轮结果 |
|---|---:|
| 严格结果表正确率（包含列名） | 20/24（83.33%） |
| 首次SQL执行成功率 | 24/24（100.00%） |
| 平均端到端耗时 | 8.02秒 |
| P95端到端耗时 | 14.55秒 |
| 总Token | 129,489 |
| 其中查询Embedding Token | 639 |
| 评测等待超时 | 0 |
| 自然发生的首次SQL失败 | 0，无法计算真实错误恢复率 |

历史报告的严格正确率为95.83%（23/24），本轮为83.33%，没有证明 SQL 结果正确率提升。保留全部4个失败：

1. `portfolio_01`：实际列名“客户ID”，参考SQL未引用标识符，被 PostgreSQL 折叠成“客户id”。行数据一致，严格列名比较失败；参考列名与题目字面要求存在不一致。
2. `portfolio_08`：结果值正确，但模型返回 `shipper_id` / `order_count`，未按要求返回中文列名。
3. `portfolio_13`：实际和参考均为408，但列名为 `order_count` 而非“订单量”。
4. `portfolio_21`：日期筛选本应返回空表，模型追加诊断查询后，展示层使用最后一次查询的统计行覆盖了空结果。这是上一阶段已经记录的多查询结果选择问题。

前三题仅在事后诊断中进行列名映射核对，确认数值一致；不修改主评分，不把本轮改报为23/24。见 [SQL失败诊断](../evals/reports/semantic-sql-diagnostics.json)。这些结果说明检索改善不能直接换算为最终答案正确率改善。聊天输出有随机性，且两轮依赖环境与网络条件也可能不同，不能把分数变化单独归因于检索。

## 工程验证与代价

- Docker 内完整自动化测试：**78项通过**，比上一阶段增加19项。覆盖分批与乱序响应、数量/维度/数值校验、错误不降级、模型与语料版本隔离、缓存用量、PostgreSQL建索引事务回滚、旧索引保留、零词面证据不产生融合票数等。
- API、Worker、PostgreSQL、Redis健康；48条新向量的实际存储维度均为1024。原哈希表仍存在。
- 首次构建48条知识消耗1695个Embedding Token；再次bootstrap为0，不重复调用接口。
- 单条真实查询缓存检查：首次392.1毫秒、14个Token；缓存命中0.2毫秒、0个Token，返回内容一致。这是一次功能检查，不是性能压测。
- 无缓存检索对照中，当前混合语义检索平均约166.26毫秒，原哈希混合约7.23毫秒。语义服务增加网络调用和费用；不是更快的本地检索。评测各方案顺序运行，SQL复测与部分检索评测时间重叠，耗时不用于性能提升声明。
- 金额仍由配置单价估算，真实费用以供应商账单为准。旧索引自动清理、增量向量化、跨实例热切换尚未实现。
